# AGENTS.md — обязательные правила для ИИ-агента

## Проект и единственная задача

Ты работаешь с фронтендом **Argilla 2.8.0**. Исправь потерю горячих клавиш для выбора вариантов ответа **после клика мышью вне вариантов ответа на странице разметки**.

**Точный воспроизводимый сценарий:** аннотатор сначала может выбирать варианты кнопками `1`, `2`, `3` (например, Yes / No / Not sure). Если он щёлкает мышью по пустой области или обычному тексту/неинтерактивному участку страницы Argilla, цифровые клавиши перестают выбирать ответы. Простой повторный клик по фону не помогает. Для восстановления требуется щёлкнуть мышью **именно по одному из вариантов ответа**; после этого клавиатурное управление снова работает. Потеря shortcuts возникает от клика вне ответов **без необходимости переключать запись**.

**НЕ связывай задачу со сменой или «перескакиванием» текстов.** Мерцание, неправильный порядок, предзагрузка, конкурентная разметка нескольких аннотаторов, переходы между записями — отдельные темы и не являются триггером или причиной, которую нужно искать по этому ТЗ.

## Начало каждого сеанса

1. Прочитай `AGENTS.md`, `docs/TASK.md`, `docs/STEPS.md`, `docs/PROGRESS.md`; для этапов 0/тестирования/развёртывания — также соответствующие .md.
2. Выполни `git status`, `git branch -vv`, `git log -5 --oneline`, `git remote -v`; не перезаписывай существующие изменения.
3. Назови текущий незавершённый этап, кратко сформулируй план и критерии готовности.
4. **В первой сессии начни с настройки GitHub и VS Code**, помоги пользователю организовать baseline, ветку, Commit и Sync Changes по `docs/GITHUB_SETUP.md`. Не редактируй исходники до появления надёжной точки отката.

## Ограничения на разработку

- Базовый ориентир — релиз `v2.8.0` (заявленный исходный SHA `78cb518`), но сначала проверь исходники и возможные корпоративные изменения. Не предполагай, что версия интерфейса означает идентичный код.
- Сначала воспроизведи проблему на **одной и той же записи**, используя последовательность «вариант ответа → клик по фону/обычному тексту → `1/2/3`». Для диагностики проверь `document.activeElement`, путь всплытия `keydown`, listeners, `blur`/`focus`, существующие глобальные shortcuts и состояние формы.
- Исследуй прежде всего `LabelSelection.component.vue`, `Questions.component.vue`, `QuestionsForm.vue` и относящиеся к ним компоненты. Приведённые пути в `TASK.md` — ориентиры для проверки в рабочем дереве.
- **Не принимать автоматически** решение через `:key="record.id"` или watcher смены записи: по уточнённому сценарию это, скорее всего, не исправит исходную проблему.
- Предпочти минимальный, доступный с клавиатуры механизм: сочетания выбора должны работать после клика по **неинтерактивному** месту активной страницы разметки. Выбирай между безопасным управлением фокусом и обработчиком клавиш на уровне страницы разметки только после аудита существующих событий.
- Глобальный `keydown` допустим лишь с точными guard-условиями и корректным подключением/отпиской, без дублирования существующих listener-ов. Не перехватывай цифры при вводе в `input`, `textarea`, `select`, `contenteditable`, поиске, открытой модалке, выпадающем меню, вне режима разметки или при `Ctrl/Alt/Meta` (и иных сочетаниях по фактическим требованиям UX).
- Не создавай `click`, `change`, `submit`, навигацию или сохранение самостоятельно через восстановление фокуса. Выбор должен проходить по существующему пути обработки ответа; нельзя ломать Enter, Tab, стрелки и доступность.
- Не переписывай загрузку записей, prefetch, порядок текстов, API, backend, права, auto-submit, сохранение ответов или маршрутизацию. Изменение этих подсистем — отдельная задача и требует явного разрешения.
- Учитывай единичный/множественный выбор, rating, несколько вопросов, подсказки shortcuts, повторное нажатие и цифровой блок, исходя из фактических компонентов.

## Тесты и контроль качества

- Сначала создай/опиши **падающий до патча** сценарий на клике по фону без смены записи. После патча он должен проходить.
- Используй Jest/Vue Test Utils и Playwright по реальным scripts проекта; подробная матрица в `docs/TEST_PLAN.md`. После основного теста проверь работу на серии кликов по разным областям страницы; 200 записей не требуются для основного воспроизведения.
- Проверяй отсутствие вмешательства в обычный ввод цифр и навигацию браузера. Не заявляй успешный тест, который не запускался.
- Используй только локальные/стендовые синтетические данные; никакого автоматического изменения настоящих рабочих аннотаций.

## Git, безопасность и отчёты

- Работай в отдельной ветке `fix/annotation-shortcuts-click-away`. Не работай в `main`, `develop` или detached HEAD. Перед каждым коммитом — diff и проверка на секреты.
- После каждого этапа обнови `docs/PROGRESS.md`, запиши команды тестов и commit SHA, создай небольшой коммит своих изменений; объясни пользователю, как сделать Sync Changes.
- Не делать `force push`, `reset --hard`, `clean -fd`, удаления чужих изменений, production deploy или публичный PR без разрешения.
- Не публикуй корпоративные тексты, токены, домены, cookies, URL внутренних систем и трейс-логи с данными. Публичный PR — только после согласования.

## Формат отчёта после этапа

1. Сделано: какие файлы и зачем.
2. Проверено: команды и PASS / FAIL / NOT RUN.
3. Git: ветка, SHA, статус Sync.
4. Риски/неизвестное.
5. Следующий этап из `docs/STEPS.md`.

При просьбе выполнить только один этап — остановись после него. Если пользователь попросил только план — не изменяй код.
