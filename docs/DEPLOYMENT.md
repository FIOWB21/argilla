# DEPLOYMENT.md — внедрение в корпоративную Argilla (только по согласованию)

## Что известно / неизвестно

Известно: интерфейс показывает Argilla 2.8.0; пользователь работает с ролью annotator в браузере. **Неизвестно:** кто управляет сервером, Docker/Compose/Helm/облачная установка, CI/CD, корпоративные патчи, фактический SHA UI-сборки. Ни один вариант внедрения нельзя считать согласованным.

## Что передать администратору

Подготовленный комплект: [PATCH_HANDOFF.md](./PATCH_HANDOFF.md) — описание, принятые SHA, результаты тестов и откат; [annotation-shortcuts-v2.8.0.patch](./patches/annotation-shortcuts-v2.8.0.patch) — накопленный патч четырёх рабочих Vue-компонентов. Применимость проверена на чистой `v2.8.0`; совместимость с корпоративными правками проверяет администратор.

- Ссылка на приватный репозиторий/доступную ветку либо diff патча без корпоративных секретов.
- Исходная база (tag + SHA), рабочий commit SHA и перечень изменённых файлов.
- Понятное описание бага: после клика по фону/обычному тексту на той же записи не работают 1/2/3; проверенный сценарий до/после.
- Команды тестов и их фактические результаты; ограничения.
- Инструкции по сборке той же версии фронтенда, совместимости с установленным backend и неизменяемый образ/артефакт, созданный администратором.

## Контрольный список внедрения

1. Проверить у ответственного реальный исходный образ/digest и наличие дополнительных кастомизаций. Патч перенести на фактическую корпоративную базу, а не заменять её всем публичным upstream.
2. Поднять **staging** с синтетическими данными и близкой к production конфигурацией. Никакой записи в реальную рабочую БД тестовыми скриптами.
3. Проверить UI вручную и автоматизированно по `TEST_PLAN.md` + корректность штатного сохранения ответов в стенде.
4. Подготовить резервную копию/точный digest существующего образа, конфигурацию deploy и понятную процедуру rollback (к предыдущему образу), назначить ответственного.
5. Получить согласование деплоя и окно работ, затем действовать по реальному CI/CD/регламенту компании. Права annotator/API-ключ не дают права модифицировать веб-сервер.
6. После внедрения выполнить smoke-test с согласованным безопасным датасетом; проверить ошибки UI и отзывы пользователей. Если регрессия — вернуть предыдущий образ по плану rollback.

## Чего НЕ делать

- Не заменять файлы на живом сервере напрямую без резервного пути и разрешения.
- Не «обновлять всю Argilla до последнего релиза» вместо точечного исправления.
- Не выкладывать в публичный PR внутренние URL, рабочие тексты, API-ключи, cookies, сетевые запросы с содержимым разметки, скриншоты с данными компании.
- Не считать Git Sync деплоем: это только передача коммитов в GitHub. Корпоративная сборка и внедрение — отдельный процесс.
