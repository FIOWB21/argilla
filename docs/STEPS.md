# STEPS.md — план работы для ИИ-агента

**Правило:** выполнять по порядку. Перед каждым этапом проверять `PROGRESS.md` и Git, после этапа записывать факты, тесты, commit SHA. Не двигаться дальше без критерия готовности. Все испытания — на локальном/тестовом стенде.

## Шаг 0 — сначала GitHub, VS Code Sync Changes и точка отката

- [ ] Коротко объяснить пользователю Commit → Sync Changes по `docs/GITHUB_SETUP.md`, помочь подготовить окружение Windows/VS Code.
- [ ] Проверить Git, авторизацию GitHub, `git status`, remotes, ветки, теги, исходную версию. Сохранить незакоммиченные изменения без потери.
- [ ] Выбрать приватный репозиторий (если публикация не разрешена) или публичный fork чистой upstream Argilla; подтвердить правила корпоративного кода.
- [ ] Сохранить точную чистую исходную baseline-ветку/тег в удалённом GitHub и создать `fix/annotation-shortcuts-click-away`.
- [ ] Добавить документы .md, сделать первый docs-коммит, настроить upstream tracking, показать пользователю Sync Changes и убедиться, что commit появился на GitHub.
- [ ] Записать в `PROGRESS.md`: URL без секретов, baseline SHA, рабочую ветку, SHA коммита и статус синхронизации.

**Готово:** есть доступная точка отката и пользователь умеет делать Commit + Sync в VS Code. **Не начинать изменения кода до этого.**

## Шаг 1 — воспроизведение на одной записи и диагностика

- [ ] Проверить фактический код версии 2.8.0; найти цепочку события клавиши и место, где она теряется.
- [ ] На тестовой записи: убедиться в работе `1/2/3`, затем **кликнуть по фону/обычному тексту, НЕ меняя запись**, нажать `1/2/3`, зафиксировать отсутствие реакции. Клик по варианту снова восстанавливает управление.
- [ ] Зафиксировать `document.activeElement` до/после клика, target/key/path `keydown`, привязку обработчика к контейнеру и наличие конфликтующих document listeners. Никаких текстов/ответов пользователей в логах.
- [ ] Разделить клик по безопасному фону и клик в `input`, `textarea`, поиске, меню, модалке, ссылке и других интерактивных элементах.
- [ ] Подготовить минимальный воспроизводимый unit/E2E тест, который падает на baseline; по возможности сохранить как отдельный тестовый коммит.

**Готово:** доказано, где именно пропадает `keydown`, воспроизведение не зависит от смены записи.

## Шаг 2 — минимальное исправление

- [ ] На основании диагностики выбрать минимальный путь: корректно обработать цифровой shortcut в контексте активной страницы разметки либо безопасно сохранять нужный фокус после клика по неинтерактивной области.
- [ ] Не перехватывать ввод в редактируемых элементах, модалках/меню, вне разметки, при модификаторах; очистить event listeners при размонтировании и предотвратить двойную обработку.
- [ ] Проверить, что клик по фону сам ничего не выбирает, не вызывает submit/navigation и не меняет текст.
- [ ] Проверить, что при нескольких вопросах выбран корректный вариант **текущего** вопроса; сохранить текущую схему переназначения цифр.
- [ ] Обновить PROGRESS.md и сделать понятный коммит, например `fix(frontend): keep annotation shortcuts after clicking background`.

**Готово:** `1/2/3` работают после клика вне ответов на той же записи; не нарушен обычный ввод.

## Шаг 3 — автоматизированная регрессия

- [ ] Тест до/после: вариант в фокусе → клик по фону/тексту → `1/2/3` → выбран соответствующий вариант, без промежуточного клика по ответу.
- [ ] Проверить отсутствие перехвата при поиске/вводе, активных меню и модалках, других страницах, сочетаниях клавиш.
- [ ] Проверить одиночную обработку, Enter/Tab/стрелки и доступность; добавить необходимые тесты Jest/Vue Test Utils и Playwright.
- [ ] Выполнить реально существующие команды `package.json`, не угадывая настройки; фиксировать PASS/FAIL/BLOCKED и логи без данных.
- [ ] Обновить PROGRESS.md и закоммитить тесты.

**Готово:** регрессионный тест красный до патча, зелёный после; нет обнаруженных критичных регрессий.

## Шаг 4 — ручная проверка и приёмка

- [ ] На локальном или staging стенде проверить **все** сценарии `docs/TEST_PLAN.md`; повторить клики в разные безопасные зоны 30–50+ раз на одной/нескольких тестовых записях.
- [ ] Дополнительно выполнить серию обычных переключений записей, чтобы убедиться в отсутствии побочных регрессий (не разыскивать баг «проскока текста»).
- [ ] Повторить в целевом браузере компании, но только с разрешёнными синтетическими/тестовыми данными.
- [ ] Заполнить протокол фактического результата, включая недоступные проверки.

**Готово:** после каждого клика по неинтерактивной области shortcuts работают, поле ввода/другие контролы не страдают.

## Шаг 5 — GitHub, передача и откат

- [ ] Убедиться, что diff содержит только релевантные изменения и нет секретов, корпоративных текстов, URL, cookies и логов.
- [ ] Завершить коммиты и Sync Changes; проверить фактические SHA на GitHub.
- [ ] Подготовить описание патча: основной сценарий, результат до/после, тесты, известные ограничения, rollback.
- [ ] При согласовании — Draft PR в upstream, иначе приватный/внутренний PR; не отправлять чужой код без разрешения.
- [ ] Передать администратору `docs/DEPLOYMENT.md`, не вносить изменения в production самостоятельно.

**Готово:** можно проверить патч в GitHub, вернуть предыдущую версию и передать компании.

## Шаг 6 — опционально: внедрение администратором

- [ ] Подтвердить инфраструктуру и реальную корпоративную базу/образ/версию.
- [ ] Проверить сборку на staging с синтетическими данными, подготовить неизменяемый образ и rollback.
- [ ] Получить разрешение и ответственного; выполнить установленную процедуру развёртывания.
- [ ] После внедрения зафиксировать smoke-test и возможность отката.

**По умолчанию:** НЕ выполнять без отдельного согласования.
